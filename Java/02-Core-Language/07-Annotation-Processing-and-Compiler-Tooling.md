# Annotation Processing and Compiler Tooling

**Target level:** Advanced → Senior  
**Scope:** Java 8–21

Reflection examines metadata at runtime; annotation processing examines program elements during compilation. Compiler and packaging tools help answer different questions: what source compiles, what bytecode was generated, what dependencies exist, and what modules are required.

## 1. Annotation processing

### Q1. What is annotation processing? *(Intermediate)*

Annotation processing is a compile-time mechanism that can inspect annotations and program elements and generate source files, class files, or other resources. It is commonly used by code-generation libraries, dependency injection tools, serializers, and metamodel generators.

It is distinct from runtime reflection. An annotation processor runs as part of compilation and uses the language-model APIs rather than requiring application execution.

### Q2. What is an annotation processor? *(Advanced)*

An annotation processor implements javax.annotation.processing.Processor, commonly by extending AbstractProcessor. It declares supported annotation types and source version, then receives rounds containing elements and annotation metadata.

Processors should be deterministic, handle multiple rounds, and avoid assuming that all generated types exist in the first round. They should emit clear diagnostics rather than failing with opaque exceptions.

### Q3. What are processing rounds? *(Advanced)*

The compiler may run annotation processing in multiple rounds. Source files generated by one round can introduce new annotated elements that are processed in subsequent rounds, until no further source is generated or processing ends.

A processor should be idempotent with respect to the elements it handles and should not repeatedly generate the same file. Understand round completion and error diagnostics when debugging generated-code builds.

### Q4. How is an annotation processor discovered? *(Advanced)*

Processors can be configured explicitly by the build tool/compiler or discovered through service-provider configuration, commonly using the processor service name in META-INF/services. Modern builds often separate processor dependencies from ordinary application dependencies.

Keep processor dependencies explicit and versioned. A processor executes during the build, so its supply chain and behavior belong to the build's trust boundary.

### Q5. What is the difference between SOURCE, CLASS, and RUNTIME retention? *(Intermediate)*

SOURCE-retained annotations are discarded by the compiler and are not present in class files. CLASS-retained annotations are recorded in class files but are not necessarily available through runtime reflection. RUNTIME-retained annotations are recorded for reflective access at runtime.

Choose retention according to the consumer. Runtime retention adds metadata that may be needed by frameworks, while compile-time tools may not need runtime reflection.

### Q6. What is the difference between an annotation target and retention? *(Intermediate)*

@Target constrains the program elements or type-use contexts where an annotation may be applied. @Retention determines how long the annotation is retained: source only, class file, or runtime.

These answer different questions. A legal target does not imply the annotation will be available at runtime, and runtime retention does not permit applying it to every element.

### Q7. What are repeatable and type-use annotations? *(Advanced)*

Repeatable annotations allow the same annotation type to appear more than once in supported contexts, using a declared container annotation. Type-use annotations can annotate uses of types, such as generic arguments or array component types, rather than only declarations.

Frameworks and processors must inspect the appropriate element/type model APIs. Do not assume every annotation is visible through the same reflective lookup method.

### Q8. How do annotation processors differ from Lombok-style compiler integrations? *(Advanced)*

Standard annotation processing uses documented compiler APIs to inspect elements and generate additional files. Some tools also integrate more deeply with compiler internals or modify compiler representations, which can make behavior more sensitive to compiler and JDK versions.

Prefer standard APIs where possible. Pin tool versions, read compatibility notes, and test upgrades because compiler integrations can break even when application source has not changed.

## 2. Compiler and bytecode tools

### Q9. What does javac --release do? *(Intermediate)*

The --release option compiles against the language rules, class-file target, and documented platform API surface for the selected Java release. It is generally a better compatibility check than setting only -source and -target, which by themselves do not ensure that newer platform APIs are excluded.

Use the release matching the minimum runtime you support. Build plugins and toolchains should be configured consistently so IDE and CI builds agree.

### Q10. What does javap help you inspect? *(Intermediate)*

javap disassembles class files and can show signatures, bytecode instructions, descriptors, flags, and other class-file details. Options such as -c, -p, -s, and -v expose different levels of information.

Use it to understand compiler-generated bridge methods, synthetic members, constant-pool references, and bytecode behavior. Bytecode output is implementation evidence for that compilation, not a substitute for the language specification.

### Q11. What does jdeps do? *(Advanced)*

jdeps analyzes class or module dependencies and can help identify dependencies on JDK internal APIs, package dependencies, and module relationships. It is useful during migration to a newer JDK or modularization.

Its analysis is static and cannot reveal every dependency created dynamically through reflection, configuration, service loading, or generated code. Combine it with tests and runtime evidence.

### Q12. What is the difference between classpath and module path? *(Advanced)*

The classpath loads classes in the traditional unnamed-module model, while the module path supports named modules and their declared dependencies, exports, and opens. Module resolution and encapsulation rules differ from ordinary classpath behavior.

A dependency working on the classpath does not prove it will work unchanged on the module path. Test reflective frameworks, service loading, split packages, and access requirements when modularizing.

### Q13. What is a multi-release JAR? *(Advanced)*

A multi-release JAR can contain version-specific class files under META-INF/versions/N, allowing a runtime to select an appropriate implementation for its release when the JAR is correctly marked and packaged as multi-release.

It can support optimized or newer implementations while retaining a baseline, but build and testing must cover every supported runtime. Inspect the JAR manifest and contents rather than assuming the directory layout alone activates the feature.

### Q14. What is the role of the ServiceLoader mechanism? *(Advanced)*

ServiceLoader discovers provider implementations for a service abstraction using supported provider configuration and module mechanisms. It decouples a caller from a concrete implementation and is used by many JDK and library extension points.

Discovery can fail because providers are missing, inaccessible, misconfigured, or incompatible. Treat provider configuration as part of deployment and test both classpath and modular packaging where relevant.

### Q15. How should compiler diagnostics and generated sources be debugged? *(Senior)*

Reproduce with the same JDK, compiler flags, build tool, processor path, and dependency versions used in CI. Inspect compiler diagnostics, generated-source directories, processor discovery, and incremental-build caches.

Temporarily disable incremental compilation or isolate processors only as a diagnostic step, then restore the intended build and fix the underlying issue. Avoid committing generated files unless the project's build policy explicitly requires them.
